# Bible-game 章節靈修內容生成

你要為「靈修冒險」（Bible-game）生成新章節的完整靈修內容。

**專案背景**：給大光教會成人查經班的每日靈修輔助遊戲。純前端 HTML+JS，內容資料在 `content.js`。

---

## Step 0: 取得任務參數

**如果使用者啟動 skill 時帶了參數**（例如 `/bible-content-generator 哥林多前書 第5章 2026-05-12 COR1_5`），直接用。

**如果沒帶參數**，問使用者四件事：

1. **書卷**（例如：哥林多前書）
2. **章數**（例如：第5章）
3. **排程日期**（例如：2026-05-12）
4. **章節 key**（按下面命名規則）

**章節 key 命名規則**：
- 使徒行傳 → 數字（例如：10, 11, 27）
- 羅馬書 → `ROM` + 章數（例如：ROM1, ROM16）
- 哥林多前書 → `COR1_` + 章數（例如：COR1_1, COR1_10）
- 哥林多後書 → `COR2_` + 章數
- 加拉太書 → `GAL` + 章數
- 之後的書卷依此類推（EPH, PHP, COL...）

---

## Step 1: 讀專案背景

執行雙角色迴圈前，先讀以下檔案了解規範：

1. `~/Desktop/Bible-game/CLAUDE.md` — 專案完整背景與設計規範
2. `~/Desktop/Bible-game/content.js` — 看現有章節結構（特別找跟新章節同書卷的範例，例如 ROM1 / COR1_1）作為格式參考

## 雙角色迴圈

你要在同一個 session 裡輪流扮演兩個角色，直到內容通過審查才停止：

- **生成專員**：根據設計規範生成靈修內容
- **審查員**：逐項檢查品質，發現問題回傳給生成專員修改

---

### 第一輪：【生成專員】執行

請以【生成專員】身份，按照以下步驟生成內容：

#### 步驟 1｜確認和合本原文
先確認本章節的和合本內容，特別記下適合引用的金句。可透過 Bible.com 查詢原文（遊戲 `BIBLE_LINKS` 裡有每章連結）。

#### 步驟 2｜撰寫 guide 導讀
- `readTime`：預估閱讀完整章節的分鐘數（3-6）
- `intro`：2-3句，整章大意，讓不熟悉聖經的人也能理解
- `outline`：3-4個段落重點，格式為「節數｜重點」
- `focus`：1句，說明今日情境題聚焦在哪裡
- `hard`（選填）：這章讀者**具體**會卡的 1-3 點，每點一句「卡在哪＋怎麼讀過去」（例：家譜不用記名字、王名只要抓住一件事）。只在真有難處時填（家譜、陌生人名地名、律法段、突然出現又消失的人物）；不寫「這章很難」之類的立場，只給幫助。不重複 intro 已講的。

#### 步驟 3｜撰寫核心內容
- `verse`：今日金句，必須是和合本原文，**一字不差**
- `verseRef`：出處（例如：—— 哥林多前書 5:7）
- `scene`：2-4句，描述今日情境背景

#### 步驟 4｜撰寫情境題
- `q`：開放性問題，連結玩家真實生命
- `choices`：4個選項（A/B/C/D），涵蓋不同信仰成熟度
  - 至少一個選項給「老實說我做不到」的人
  - **四格立場自標**：每格在心裡標一個 tag（現況／情緒／理性／退縮），四格不得有三格同 tag；四格是不同立場，不是同一種軟弱的四種強度
  - **配額**：軟弱－掙扎－受傷光譜至多兩格；至少一格給「我已經在做了／這對我不難」或「這章我沒特別感覺」
  - **路徑輪替**：tone-guide 的路徑 A（情緒對位）連續 3 章不得都用；雷區章可豁免並在審查時註明
  - 用真實的人話，不用宗教術語
- `responses`：對應4個選項的回應
  - 溫暖有洞見，像朋友同行，不說教——但不說教≠沒重量：每章至少一則回應含「經文說了什麼／沒說什麼」的觀察句，挑戰落在經文上、不落在玩家人格上
  - 每個回應最後留下「**一個情緒有重量的小步**」（真實的人會說出口的話，或有方向感的問題）；四格的小步不得都是「跟神說一句話」——現況格的小步輪替「對人的動作／對自己的一句話／什麼都不做只記一句」，不得連續兩章都是「去找一個人」（避免「過得好＝該去服事別人」的隱性功課）

#### 步驟 5｜撰寫默想
- `reflectionTitle`：2-4字主題
- `reflection`：兩段，第一段聖經背景，第二段個人問題

#### 步驟 6｜設計裝備
- `baseItem`：完成靈修獲得，emoji + name + desc + slot
- `bonusItem`：填寫默想後獲得（稀有），emoji + name + desc + slot
- `desc` 必須是真實的和合本原文，**一字不差**
- 名稱和 desc 必須在同一個神學層次
- 判斷本章是否適合做性別差異裝備：
  - 若經文有明確的性別角色意象（如才德婦人、勇士）→ 可用性別格式
  - 性別格式：`{ default:{...}, m:{...}, f:{...} }`
  - 大部分章節不需要，只在自然適合時才用

完成後，輸出完整的 JavaScript 物件。

### 第二輪：【審查員】執行

【生成專員】完成後，立刻切換成【審查員】身份，逐項審查：

#### A. 格式完整性
- [ ] 所有必要欄位是否齊全
- [ ] `choices` 是否剛好 4 個（A/B/C/D）
- [ ] `responses` 是否對應 4 個選項
- [ ] `guide` 是否有 `intro` / `outline` / `focus`
- [ ] `baseItem` 和 `bonusItem` 是否有 `emoji` / `name` / `desc` / `slot`

#### B. 和合本核對（**上網驗證**）
- [ ] 透過 Bible.com 或 BIBLE_LINKS 查詢原文，逐字比對以下欄位：
- [ ] `verse` 是否為真實和合本原文（用字、標點是否正確）
- [ ] `baseItem.desc` 是否為真實和合本原文
- [ ] `bonusItem.desc` 是否為真實和合本原文
- [ ] **截斷經文等同引用錯誤**，整節太長要換節而非截半
- [ ] 兩個裝備不能拆同一節經文

#### C. 情境題品質
- [ ] `q` 是否連結玩家真實生命，而非純知識測驗
- [ ] 四個選項是否涵蓋不同信仰成熟度——四格 tag（現況／情緒／理性／退縮）是否有三格相同（有 → 需修改）
- [ ] 軟弱－掙扎－受傷光譜是否 ≤2 格；是否有一格給「我已經在做了」或「沒特別感覺」
- [ ] 是否有「老實說我做不到」的選項
- [ ] 本章是否連同前兩章都用路徑 A 情緒對位（是且非雷區 → 換路徑 B/C）
- [ ] 本章題目主題（被看見／孤單／被遺忘⋯）是否與前兩章重複（是 → 換角度提問）
- [ ] 每個 `response` 是否有「情緒有重量的小步」；四格小步是否都是「跟神說一句話」（是 → 現況格改對人或對自己）
- [ ] 現況格的小步是否與前一章同型（前一章「去找一個人」→ 本章改對自己或不做）
- [ ] 是否至少一則 `response` 含「經文說了什麼／沒說什麼」的觀察句
- [ ] `responses` 是否有說教語氣（有 → 需修改）

#### D. 裝備設計
- [ ] `baseItem` 名稱和 desc 是否同神學層次
- [ ] `bonusItem` 名稱和 desc 是否同神學層次
- [ ] `baseItem.desc` 引用的經文是否在本章範圍內（**不可跨章引用**）
- [ ] `bonusItem.desc` 引用的經文是否在本章範圍內（**不可跨章引用**）
- [ ] `verse` 引用的經文是否在本章範圍內（**不可跨章引用**）

#### E. 人話自檢
- [ ] `choices` 的文字是真實的人會說出口的嗎
- [ ] `responses` 的文字自然，不像官方聲明或勵志貼文嗎
- [ ] `scene` 讓不熟悉聖經的人也能理解情境嗎

#### F. guide 導讀品質
- [ ] `intro` 是否幫助玩家對整章有初步認識
- [ ] `outline` 是否清楚列出本章結構重點
- [ ] `focus` 是否說明了今天情境題的聚焦點
- [ ] `hard`（若有）每點是否都是「具體卡點＋怎麼讀過去」，而非「這章很難」的評語；沒難處是否留空

## 迴圈規則

審查完成後：

**如果有任何 ❌**：
- 切換回【生成專員】
- **只修改有問題的部分**，不動通過的部分
- 修改完畢，切換回【審查員】重新審查有問題的項目
- 重複以上步驟，直到所有項目通過

**如果全部 ✅**：
輸出以下內容給使用者確認：

```
---
✅ 審查通過 · 共迭代 [N] 輪

[完整的 JavaScript 物件]

審查摘要：
- 迭代輪數：N 輪
- 修改項目：[列出曾修改過的項目]
- 和合本核對：已確認 verse / baseItem.desc / bonusItem.desc
---
```

等使用者確認後，再更新 `content.js` 並 git push。

## 參考備註

**關於迭代輪數**：一般內容 1-2 輪就會通過。如果超過 3 輪還有問題，通常是和合本經文確認困難，可以請使用者手動指定經文讓繼續。

**完成後的輸出位置**：
1. 把生成的 JavaScript 物件貼到 `content.js` 的 `CHAPTERS` 陣列內
2. 在 `SCHEDULE` 加排程日期 → 章節 key 對應
3. 部署到 dev preview 讓使用者驗證
4. 沒問題後 commit + push

**設計原則提醒**（從 LEARNING.md / memory）：
- 玩家輸入文字（默想、回饋）是核心資產，預設要存 Firestore
- 默想是悄悄話，不加查看工具
- 儀式感優先，不為了簡化犧牲動畫感
- 引號內文字必須是和合本原文，敬語用「他」不用「祂」
