# ADR 0002：內容產線收斂為 Claude Code 一條龍

- 日期：2026-08-24
- 狀態：已採納（James 拍板：審稿方式、啟動方式、視窗退役三題皆照建議）
- 關聯：ADR 0001「尚未定案」之產線收斂項；CLAUDE.md「多視窗協作模式」

## 背景

原產線：James 想排程 → 到 claude.ai「內容生產」視窗生成 → 手動複製搬到 Claude Code → 寫入、驗證、部署 → 再確認。模式固定，但 James 本人是輸送帶，每批要切換多個視窗搬運多次。James 的明確要求：「怎麼樣我最省事」。

前提已成熟：語氣指南（`content-tone-guide.md`，27KB）、格式慣例、`bible-content-generator` skill、`validateContent()` 七條不變量與 `npm test` 守門都已在 repo，CC 拿得到與內容視窗完全相同的材料。

## 決策：三段一條龍

- **A1 生成＋自驗**：CC 直接生成每日內容。語氣照 `content-tone-guide.md`、格式照最近一批慣例（勿用全檔歷史樣本推論）；**每句經文（verse／裝備 desc）逐一以和合本官網 CUNP1 驗證**（`https://rcuv.hkbs.org.hk/CUNP1/{book}/{chapter}/`，頁面標記為準，HTTP 200 不算）；結構過 `npm run validate:content` 與 `npm test`。
- **A2 寫入＋預覽**：寫入 `content.js`（含 SCHEDULE 展開，依 repo 內教會進度文件）→ 測試 → 部署 dev 預覽頻道 → 開 PR。給 James 一則訊息：預覽網址＋三個建議抽查點。
- **A3 節奏**：每週一批、供應下一週。**啟動＝James 丟一句「出下週內容」**（跑穩兩三週後再評估升級為排程自動產）。James 手機上以玩家身分玩 dev 預覽審稿，回「OK」或指出問題 → 修正 → James 合併 PR。

### James 的三個拍板

1. **審稿方式**：玩 dev 預覽網址（玩家視角最能抓「乏味感」）＋ CC 附三個抽查點；不逐字讀全文。
2. **啟動方式**：先手動喊，信任建立後再自動化——「自動化要建立在信任成品之後」。
3. **內容生產視窗**：退役但不刪，留作歷史檔案；內容相關討論全部進 CC。

## 模型分級（2026-08-24 晚，James 拍板「感受上差不多」）

寫作是產線唯一吃模型等級的步驟（其餘全是腳本），且輸出 token 比輸入貴約五倍，故分級：

- **平常章 → Sonnet**：以子代理或獨立 Sonnet 工作階段生成。試點＝創 24（Sonnet 依同一套材料生成，四處引文逐字驗證通過，James 盲測「感受上差不多」）；試稿存 `drafts/gen24-sonnet-draft.js`，9/21 批修兩處小地方後入庫。
- **雷區章 → 高階模型**：語氣指南點名的重章（如創 19 所多瑪、創 22 獻以撒）錯的方式微妙、護欄擋不住語氣，由高階模型寫。
- **主編審查與寫作分屬不同腦**：Sonnet 寫、高階模型當主編過一輪，避免「自己寫自己審」的語氣盲點；腳本護欄不分模型一律跑。

護欄轉正：`npm run verify:scripture <章節key...>`（`scripts/verify-scripture.js`）＝經文逐字比對＋欄位完整性的單一正本，任何模型寫的稿都過同一關；`--dump` 模式供生成前抓 CUNP1 原文。

## 已知風險與對策（2026-08-24 盤點）

- **同質化＝最大盲區**：產線讓生產變順，但批內句式易重複（如情境題連用「你有沒有過⋯」），與「重新點燃」的初衷相牴觸。對策：批內刻意變化題型與提煉路徑配比；James 審稿專看「連讀七天會不會膩」。
- **回饋迴路**：每週產新批時，順帶回報上一批的完成數與默想數（即核心指標口徑），讓內容有成績單。
- **10 月斷糧點**：教會進度表只列到 9/30，9 月中需向教會要 10 月排程。（已解：2026-08-30 全年進度定案，見 CLAUDE.md「讀經進度對應」）
- **James 實際要按兩次合併**：內容 PR→dev（審稿後）＋dev→main（上 prod）。CC 兩個 PR 一起備好。
- **行文用字**：行文一律「什麼」，只有經文引用保留「甚麼」（GEN11-17 首批混用 10 處已修正）。
