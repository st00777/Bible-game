# ADR 0003：多視窗分工收斂為 Claude Code 單一執行者

- 日期：2026-08-28
- 狀態：已採納（James 於 Claude Code 遠端會話拍板「動手吧」）
- 關聯：ADR 0001「尚未定案」之多視窗收斂項；ADR 0002（內容生產視窗退役的先例）；CLAUDE.md「多視窗協作模式」；`roles/README.md`

## 背景

原架構「5 個策略視窗（claude.ai）＋ Claude Code 執行者」。實際運作中：

1. **每個視窗都會因上下文過長而換新**，PM 視窗已換過多次。換視窗要靠交接卡（`pm-handover.md` 405 行、`dev-coord-handover.md` 313 行…），新視窗還要花數輪對話「重新回到角色定位」。
2. **新視窗掌握不了最新狀況**，必須開工單給 CC「調查現況並回報」，再依回報決策——CC 早就知道的事繞一圈才回到決策者手上。
3. James 已改用手機遠端（Remote Control）直接與 CC 對話，「跟 PM 對話」與「跟 CC 對話」對他而言體驗相同，多視窗剩下的只有搬運成本。
4. ADR 0002 已證明「視窗收進 CC＋腳本護欄」可行（內容產線）。8/27 六角色評估實際上也是 CC 以 subagent 扮演六個視角完成，「多視角」不需要多視窗。

前 PM 視窗曾提出兩個顧慮：**溝通成本**（策略與執行混在同一對話）與**滾雪球成本**（單一對話越長越貴）。評估：滾雪球在視窗架構下同樣存在（正是視窗要換的原因），CC 反而有 `/clear`、`/compact`、subagent 隔離可主動控制；溝通成本的解法是分會話而非分視窗。

## 決策

1. **五個策略視窗全部退役**（PM 總指揮、開發協調、美術協調、數據分析；內容生產已於 ADR 0002 退役）。**唯一保留給 James 的角色是拍板。**
2. **CC 為單一執行者兼策略推理者**：整理選項、寫 ADR、量尺過濾、開 PR、部署，都在 CC。需要特定視角時以 subagent 扮演（PM 反方、美術、數據），讀同一份 repo，不需交接。
3. **策略與執行分會話**：策略討論與執行工單各開 CC 會話、`/rename` 標名，避免混在一起（回應前 PM 的溝通成本顧慮）。
4. **交接卡退役**：三份 handover 歸檔至 `docs/history/*-handover-2026-08.md`。CC 的交接卡＝repo 本身（CLAUDE.md「近期待開發功能」＋「戰略對焦」、ADR、memory、git log），每次開會話自動載入，不需人手搬運。
5. **claude.ai 專案知識庫同步停做**：沒有視窗要讀它了。
6. `roles/*.md` 留檔不刪，作為未來 subagent 定義（`.claude/agents/`）的改寫材料——**尚未改寫，列為後續事項**。

## 四個盲點與對應守則

| 盲點 | 說明 | 守則 |
|---|---|---|
| **執行者自我評分** | 提案與執行同一對話，會傾向同意自己的提案；原本 PM 視窗的退單閘門（如 6/5 否決日記 v2）消失 | 重大決策（新功能、上正式版、殺併留）前開一個**不帶當前上下文的 subagent 扮 PM 反方**，要它反對，輸出後 James 再拍板 |
| **權限與影響範圍** | PM 視窗只能講話；CC 能 deploy、動 Firestore。策略聊天裡一句「那就上吧」在 CC 是指令 | 上正式版／`firebase deploy`（functions、rules）／改 schema 一律在策略對話外**單獨明確確認**，不在聊天中順口帶過 |
| **思考痕跡沒地方去** | PM 視窗對話本身記錄「為什麼猶豫、否決過什麼」；CC `/clear` 後就沒了，半年後會重提舊提案 | ADR 加「否決紀錄」（每個被否決提案一行＋理由）；James 的顧慮與判斷（如「召回牌只能打一次」）寫進 memory |
| **單點故障** | 全靠一個工具 | 影響小：claude.ai 與 repo 都在，隨時可開臨時對話；不另設備援 |
